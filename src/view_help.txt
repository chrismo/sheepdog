sd view - the Flock page: every branch sd watch tracks, where its PR stands
and who moves next, live in the browser; the Atlas, how the workflow works;
the Map, the code behind it.

Usage: sd view [<branch>] [--port <n>] [--no-open]

  Starts a local server on 127.0.0.1, prints its URL and opens it in the
  browser, then serves until Ctrl-C. With one already on the port, it opens
  that one instead, unless that one is an older build: then it stops it and
  starts in its place.

  <branch> opens on that branch's drill-in: . for the current worktree's
  branch, or a branch's exact name, its PR number, or a part of its name
  (any case: sd view atlas-w). Several matches or none are listed, and
  nothing starts.

  The page reads the state each sd watch pass caches, and asks again every
  30s. It shows the last pass's time: with the watcher stopped, that time
  stops moving. Each branch is a fence line, grouped by who moves next: its
  seven stages are posts, a tally stroke on each one done, a cross on a
  failing one, and a paint mark in the mover's color where it stands; a
  stage not set up has no post. A branch's timeline has its PR's commits,
  CI and merge from GitHub (gh). A branch is there from its first pass, and
  stays until the watcher drops its cache: after it's unenrolled, or once
  its merge is notified.
  A row's branch name links to its drill-in, so it opens in a new tab too;
  the drill-in's tab is titled by its branch and repo.
  A group's count shows only that group, and a repo in the top line only
  that repo; the text box (/ focuses it, Escape clears it) keeps branches
  whose name, repo or PR number has its letters in order. The filter is in
  the URL (#who=you&repo=kinsite&q=fact), so it links and reloads.

  The Atlas (/atlas, linked from the Flock and the Map) is the workflow
  itself, generated from the code so it can't drift: every NEXT step by the
  Flock's seven stages, with who does it and a line on what it means
  (src/next/steps.rs). It opens on the world: the nine steps in no stage,
  then the seven stages top to bottom, each a line of its happy path's
  words, the steps it takes when nothing is wrong, in the time order
  declared on each step's row (StepDef::path; NEXT's own list is a priority
  order and never reads it), and a count of its exceptions. A path step the
  stage always takes is outlined in color; one taken only under a condition
  is dashed and muted, its condition on hover and in the open stage
  (path_if: behind, when the target moved). The steps in no stage open by
  what each does to NEXT's list (StepDef::hold): busy, the list is running
  alone; unsure, a warning above it (errors, stale, gh-wait); whose move,
  above it while it stands (attached, foreign, question); stand-in, in place
  of the agent steps (budget, failed). A stage opens into its path, then off
  the path: the steps NEXT offers when the stage can't take its next path
  step, grouped by whose move gets it back on (chrismo, an agent, sheepdog,
  others). Under "check order" an open stage's steps are one list in the
  order NEXT checks them. A step opens into its verb's gate
  (src/act/gates.rs): each rule's level as what --force does with it (force
  can't, force passes, warns, nothing to do, setting holds) and what clears
  it, then what else is checked: the running marker before the gate (force
  can't), and an attached session once the gate lets the verb run, or first
  for a verb with no gate (force passes). The step's panel also lists the
  settings it reads, each with this repo's value and the layer it comes from
  (sd config explain) and a copy button for the sd config set command that
  changes it. It reads no branch's state: only the repo's config.

  The Map (/map, linked from the Flock and the Atlas) is sheepdog's own code: each file
  under src/ sized by its lines, the share of it in functions over clippy's
  cap (tests/lint-ratchet.txt), and the open issues that name it (one gh
  issue list). Files are grouped by the stage they serve: watch loop,
  observe, decide, act, agent steps, records, settings, pages, plumbing. A
  trend strip above them samples the last commit of each day since the
  split (2026-10-13): lines in src/ and tests/, and functions over the cap.
  It reads the checkout sd was built from, whatever repo sd view runs in.

  The three link into each other: a step in a branch's drill-in opens that
  step in the Atlas; an Atlas step lists the branches whose next step it is
  now, each opening its drill-in, and the files behind it (its verb's under
  src/act/, its gate, the step table), each opening in the Map; a Map file
  lists the Atlas steps that live in it. The drill-in's Flow is the fence's
  seven stages, with the ci-fix and fix findings loops beside CI and
  Review; each of its boxes opens in the Atlas too.

  GitHub data is cached under <state>/github/ and served at once; the first
  read after it's a minute old fetches it again in the background, so with
  no page open nothing is asked. A file not fetched for a week is deleted.
  The Map and a branch's timeline show its age and have a refresh button.
  While the Flock is open, a branch whose cached state is a minute old is
  checked again (sd watch refresh), one at a time, and its row shows when;
  its refresh button checks every branch again.

  A branch's drill-in has a button for NEXT's first step when it's the
  agent's or sheepdog's: it runs sd act <verb> <branch> in the branch's
  repo, the same command the watcher's autoRun pass launches for that step,
  under the same timeout (SHEEPDOG_WATCH_TIMEOUT, settings.stepTimeout),
  one step at a time; the branch is checked again when it ends, so the page
  shows the result. The step runs only if it's still NEXT's first; your
  steps and waits have no button, and neither has any step on a PR autoRun
  leaves alone: one someone else wrote, or whose remote has their commits. The step is sd view's: Ctrl-C ends it as
  it would a hand-run sd act, and sd view's log says it was stopped.

  The drill-in also shows the branch's settings (sd config explain), each
  with the layer it comes from. settings.autoRun, reviewRounds and
  stepBudget can be set there: the page runs sd config set --branch
  <branch>, so the value goes through sd config's own checks and lands in
  the branch's file. The rest, interval among them (global file only), it
  shows.

  The foot of each page picks its look: four palettes (Drystone, Fleece &
  Raddle, Heather Moor, Lamplight), four display faces (Londrina Solid,
  Alfa Slab One, Big Shoulders Display, Familjen Grotesk), and light or
  dark. The picks are this browser's own (localStorage); without them, it's
  Fleece & Raddle and Londrina Solid, light or dark as the system is. The
  fonts are compiled into sd (fonts/), so the pages need no network.

  --port <n>   the port (default 7377; 0 picks a free one)
  --no-open    print the URL, don't open the browser
