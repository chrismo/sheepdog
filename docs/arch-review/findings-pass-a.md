## Design-level observations

**The architecture has one real seam problem and it explains a third of the open issues.** Observe → NEXT → Act was designed so that NEXT's ordering and the verbs' guards are the same facts (as-intended §3). As built they are the same *facts* read twice and judged twice, in two vocabularies, and nobody checks that the judgments agree. `state.rs` even puts NEXT's verdict into the JSON every verb reads, and the verbs ignore it. Eleven next.rs issues, #326's text, and the `next.rs`+`state.rs` co-change rate (9 of 12 commits) are all this. The fix is not a rewrite: the gates already exist as functions over the state JSON in two of five verbs (`restack_gate`, address's `gate`); the work is giving the other three the same shape (A3), making restack's gate pure (A1), and having NEXT call them. After that a NEXT-offers-what-its-gate-refuses bug is structurally impossible, and the help's "Notified" list can be generated (A4).

**Two functions hold the design, and their seams are already drawn.** `next::steps` and `state::observe` are 1,100 lines between them, but neither is a tangle: `observe` is sectioned by the O-labels from AGENTS.md, and `steps` is a predicate block followed by an ordered list. They are long because the data is assembled in one literal, not because the logic resists splitting. Splitting along the existing comments (A9, A10) is mechanical and would make the ~40 predicates unit-testable for the first time; today every NEXT rule is tested only through a hand-written JSON fixture.

**The yardstick's three assumed invariants split two ways.** gh and git centralization (I12, I13) were never stated as design goals, and the code shows why they drifted: the central runner lacked an option (env vars for git; timeout, repo targeting and error classification for gh), so each site worked around it. I'd adopt both, scoped to "one runner" rather than "one module", because the gh case has a real consequence (nine un-timed calls under a running marker) and the git case costs one small function. The third, I11, I'd restate rather than enforce: an Observe layer that caches what it saw is fine; one that writes a decision is not. The sd-pr dual meaning (A8) is the thing actually worth fixing there.

**The one cycle is one line.** `config → act::plain_words` is the only edge that stops the module graph being layered. It's a regex that knows Claude Code's permission grammar, sitting in the act layer because that's where it was first needed. A leaf module fixes it (A7), and once the graph is acyclic, "which layer is this in" becomes a question `cargo modules` or a test can answer, rather than a reading exercise.

**Help text is the spec, and that's the right call for now; make the code read it.** The three help files churn with every feature because they are where the step vocabulary and policies are written down first. That's a good habit for a one-person project. The cost is the four hand-synced copies in A4. A `StepDef` table turns the help from a thing you keep aligned into a thing you render, and gives the watcher, NEXT and the tests one source of truth for which steps exist and what each means.

**What this pass did not judge:** state and idempotency (pins, markers, failure records: pass B), the agent boundary (prompts, harness.rs, outcome parsing: pass C), and the test suite's shape beyond the I5 and NEXT-coverage points above.
